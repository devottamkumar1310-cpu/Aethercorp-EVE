# EVE Security Audit & Threat Model Analysis (Phase 8.1)

This document details the security architecture, audit findings, and threat mitigations implemented to ensure production readiness for AetherCorp EVE's public beta.

---

## 1. Multi-Tenant Isolation
- **Goal**: Prevent Org A from accessing, viewing, or modifying Org B's data (IDOR).
- **Architecture**:
  - Every business database entity (e.g., `Product`, `InventoryItem`, `SalesRecord`, `Revenue`, `Expense`, `Task`, `ExecutiveConversation`) contains a foreign key `organization_id` pointing to the tenant (`Organization`).
  - Active tenant identity is securely extracted from the custom request header `X-Workspace-Id` via the dependency `get_active_workspace_id`.
  - The dependency verifies that the authenticated user holds a valid `Membership` in the target workspace. If not, a strict `HTTP 403 Forbidden` response is returned.
- **Verification**:
  - Automated integration test `test_tenant_isolation_idor` asserts that any attempt to use a tampered workspace ID returns `403 Forbidden`.

---

## 2. Authentication & JWT Hardening
- **Goal**: Secure API endpoints against unauthorized request hijacking and token tampering.
- **Architecture**:
  - JWT tokens generated by Supabase Auth are validated symmetrically using `settings.SUPABASE_JWT_SECRET` (HS256) or asymmetrically via JWKS (`settings.SUPABASE_URL`) if configured.
  - Verification validates:
    - **Expiration Time (`exp`)**: Expired tokens return `HTTP 401 Unauthorized`.
    - **Audience (`aud`)**: Must match `"authenticated"`.
    - **Signature Validity**: Mismatched or tampered signatures return `HTTP 401 Unauthorized`.
- **Verification**:
  - Automated integration test `test_jwt_validation_failure` validates that tampered/expired tokens are successfully blocked with `401 Unauthorized`.

---

## 3. Role-Based Access Control (RBAC)
- **Goal**: Protect administrative operations (observability metrics, costs, usage stats, product analytics) from standard workspace members.
- **Architecture**:
  - A strict authorization guard `verify_workspace_admin` is applied to all GET observability routes and `/analytics/products` route.
  - The guard retrieves the user's `Membership` role for the active workspace and raises an `HTTP 403 Forbidden` exception if the role is not `"admin"` or `"owner"`.
- **Verification**:
  - Automated integration test `test_admin_authorization` confirms that standard members are blocked from admin resources while workspace admins gain access.

---

## 4. SQL Injection & Cross-Site Scripting (XSS)
- **Goal**: Secure query and user input handling.
- **Mitigations**:
  - **SQL Injection**: EVE utilizes SQLAlchemy ORM parameter binding for all database queries. Raw SQL strings are entirely avoided except where explicitly bound using `sqlalchemy.text()`.
  - **XSS**: User inputs are sanitized. Rich textual analysis is parsed via Pydantic schema validation before processing.

---

## 5. Mass Assignment Protection
- **Goal**: Prevent attackers from overwriting internal DB columns (e.g., changing workspace membership roles or model IDs during updates).
- **Mitigations**:
  - Routes do not bind raw HTTP request payloads directly to database model classes.
  - Every write operation defines strict Pydantic request schemas (e.g. `ProductCreateRequest`), explicitly filtering allowed request parameters.
